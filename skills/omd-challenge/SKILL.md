# oh-my-dsh · Challenge 红队质疑

**站在反面**：`review` 审的是已经写出来的代码，`deep-analyze` 多角度铺开一幅全景，`first-principles` 从事实重建方案——但它们都容易停在「这个方案能成立」。本技能只做一件事：**尽最大努力证明它不成立**。目标是让方案的漏洞在采用前暴露，而不是在上线后。

这是对抗性纪律，不是抬杠——每条质疑必须可被证实或证伪，攻击完要给出「要不要改」的裁决。

## 何时用

- 一个方案/结论看起来很顺，需要 adoption 前的最后一道对抗性检查。
- 用户说「这靠谱吗」「找漏洞」「有没有没想到的」「挑毛病」。
- 决策代价大、不可逆，或一个判断由单一信息源得出。
- 团队/代理刚刚高度一致地赞成某事——一致性本身就是风险信号。

**不要用**：还没方案时（先 plan/ralplan）；情绪性否定（「我不喜欢」不是质疑）；纯代码缺陷扫描（用 review）。

## 质疑纪律

1. **先把对方立场写强**：在攻击前，用一段话把方案最强的形式复述出来（ steelman ）。打稻草人毫无价值——如果你能轻易驳倒一个弱化的版本，说明你还没碰到真问题。
2. **分五个攻击面，逐个过**：
   - **前提**：它依赖哪些假设？哪个假设最经不起查？有没有 `[待验证]` 却当事实用的？
   - **反例**：什么输入/场景会让它失效？找一个具体反例胜过十句「可能有问题」。
   - **代价**：它省掉的成本，是否转嫁到了别处（维护、迁移、认知负担、兼容性）？
   - **失败模式**：它怎么坏？坏了之后怎么发现、怎么回滚？有没有静默失败？
   - **边界**：它在什么规模/量级/环境下失效？在极端值（0、空、满、并发、长上下文）下如何？
3. **质疑必须可验证**：每条写成「如果 X 成立，那么方案会在 Y 场景失败」——能被后续测试或事实确认/推翻。**「感觉不稳」不算质疑**。
4. **给严重度分级**：每条标 `致命`（会让方案整体不成立）/ `重要`（需改设计）/ `次要`（记录即可）。不分级等于把所有问题摊平，反而无法决策。
5. **反证之后给裁决**：攻击结束时明确三选一——`采纳`（质疑都被挡住，列出为何挡住）/ `修改后采纳`（列出必须补的护栏）/ `否决`（哪条致命质疑无法化解）。**只挑毛病不给裁决是半途而废**。
6. **守住对抗与破坏的边界**：质疑的是方案和结论，不是人。目标是让决定更稳，不是赢得辩论。

## 与其它模式的关系

- `deep-analyze` 铺开全景 → 本技能从全景里挑最软的地方戳。
- `ultrathink` 穷举边界与失败模式 → 本技能把列出的风险升级成具体可验证的攻击。
- `first-principles` 重建方案 → 本技能检验重建的方案是否还带着没拆干净的假设。
- `review` 在**实现后**审代码缺陷；本技能在**采纳前**攻方案本身。两者时序不同，别互相替代。
- 发现了真实缺陷要修，转 `omd-plan` → `omd-execute`；质疑的是历史决策前提，转 `omd-postmortem`。

## 收尾：HUD

用 `omd-hud` 输出：

- **方案 steelman**：一段话的最强形式陈述。
- **攻击面矩阵**：攻击面 / 质疑（可验证句式）/ 严重度 / 证据或反例。
- **裁决**：采纳 / 修改后采纳 / 否决 + 必须补的护栏清单。

让「戳了哪里、戳穿没有、结论怎么变」一眼可见。

## 反模式

- **别打稻草人**：刻意弱化对方立场再驳倒，是自欺。先 steelman。
- **别为否定而否定**：质疑要能落到可验证的失败条件上，纯情绪否定没有价值。
- **别只攻击不裁决**：列一堆问题然后说「你自己看着办」等于没做。
- **别把全标致命**：什么都致命就是什么都不致命。严格分级。
- **别攻击人**：质疑方案与结论，不评价提出者的能力或动机。

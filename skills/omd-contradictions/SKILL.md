# oh-my-dsh · Contradictions 抓主要矛盾

**排序**而不是铺开：`deep-analyze` 把多个视角铺开，`ultrathink` 穷举边界与失败模式，但都不回答一个问题——**当好几个问题同时成立、资源只够做一件事时，先做哪个？** 本技能用一套朴素但锋利的纪律回答它：复杂局面里必有一个当前起决定作用的矛盾，抓住它，其余的会松动。

这里的「矛盾」就是一对同时成立、互相拉扯的张力（A ↔ B），不是逻辑矛盾，更不是修辞。

## 何时用

- 多个问题同时报错、多个目标争抢资源，不知道先做哪个。
- 用户说「千头万绪」「先解决哪个」「哪个是关键」「抓重点」。
- 一个方案里全是权衡，需要认领当前主线，而不是列一张平铺的利弊表。
- 局势变了，怀疑之前的问题排序已经过时。

**不要用**：只有一个明确问题时（直接 debug/execute）；纯情绪发泄；把本技能当「一切都是矛盾」的万能标签。

## 分析纪律

1. **列矛盾对，不列问题点**：把局面拆成若干对同时成立的张力，写成 `A ↔ B`——「交付速度 ↔ 架构质量」「功能覆盖 ↔ 性能」「精度 ↔ 速度」「短期产出 ↔ 长期可维护」。只写单点问题等于没开始。
2. **用证据定主线，不靠感觉**：逐对问「它是否规定或影响着其他对的存在与发展？」——即**哪一个不解决，其他都白搭**。判据必须是可验证事实：数据、报错链、依赖关系、最近的失败记录。**判据带不出来就标 `[待验证]`，先去查，别硬排**。
3. **只认领一个当前主线**：明确写「本阶段只解决 X ↤ Y」。同时抓两个主要矛盾等于一个都没抓。其余矛盾不是不管——标注为「次要，待主线松动后处理」。
4. **定矛盾的主要方面**：在选中的那对张力里，判断当前哪一边起决定作用。例：「性能瓶颈的主要方面是 KV cache 溢出到 CPU，不是模型位数」。主要方面找错，力气全废。
5. **写转化条件**：主次不是永恒的。写下什么可观测信号出现时，排序该变——流量量级、成本拐点、团队规模、某个依赖的废弃。**这与 `decision-record` 的推翻条件联动**：主线变了，当初基于旧主线做的决策要重估。
6. **方法匹配**：不同质的矛盾用不同质的方法解决。对抗性张力（要 A 就得牺牲 B）与可协同张力（能创造条件让双方转化）解法不同——别拿同一招套所有。例：精度与速度的矛盾可以靠量化分级化解，而不是二选一。

## 与其它模式的关系

- **先 `deep-analyze` 铺开多视角，再用本技能排序选主线**——这是标准串联：一个负责广度，一个负责决断。
- `ultrathink` 穷举边界；本技能从它列出的清单里挑出决定性的那一个。
- `first-principles` 从事实层重建方案；本技能决定「先重建哪个」。两者可串用。
- 主线选定后用 `omd-plan` 落地；主线的取舍与推翻条件用 `omd-decision-record` 固化。
- 复盘发现当初主线选错，用 `omd-postmortem` 挖假设层。

## 收尾：HUD

用 `omd-hud` 输出三块：

- **矛盾对清单**：A ↔ B / 相互影响的证据 / 主次判定（主线·次要·待验证）。
- **主线裁决**：当前主线 / 主要方面 / 为什么它决定其他 / 本阶段不做什么。
- **转化雷达**：信号 / 如何观测 / 当前状态（未触发·临界·已触发）/ 触发后的新排序。

让「先打哪个、为什么是它、什么时候改打别的」一眼可见。

## 反模式

- **别当万能标签**：「一切都是矛盾」等于什么都没说。本技能只用于**多问题争资源**的场景，单问题直接用 debug/execute。
- **别同时抓多个主要矛盾**：列出了三四条主线就是没排序。逼自己认领一个。
- **别脱离证据排主次**：「我觉得这个更重要」不算判据。带不出证据就标 `[待验证]` 先去查。
- **别把对抗当协同**：有些张力确实此消彼长，硬说「可以两全」是自欺；另一些确实能靠结构性改动同时化解。分清是哪一种再选方法。
- **别忽略转化**：主要矛盾变了还按老主线推进，是很多长期项目空转的根源——转化信号必须写下来并定期回看。

# oh-my-dsh · Postmortem 事后复盘

**往回看**而不是往前修：`debug` 修当下，`review` 审当前 diff，`postmortem` 回答一个不同的问题——**这件事为什么会发生、防线为什么没拦住、下次怎样让它根本走不到那一步**。触发它的通常是「白干了」「空转了很久」「同样的坑又踩一次」。

## 何时用

- 一次失败、长时间空转或返工之后——尤其是投入与产出严重不成比例时。
- 用户问「为什么会这样」「怎么防止再犯」，而不是「怎么修」。
- 同一个问题第二次出现（第一次修了但没防住复发）。
- 不要用它替代 `debug`：线上正在崩、要先恢复服务时用 debug，事后才开复盘。

## 复盘纪律

1. **先锁事实，再谈原因**：把关键事件按时间排成线——何时开始、何时第一次出现异常信号、何时做了什么决策、何时确认失败。每条带来源（日志/文件时间/对话记录/监控）。**没有时间戳的「大概」不算证据**。
2. **根因分三层，别停在第一层**：
   - **直接原因**：当场让它失败的那个点（报错、坏路径、错误输入）。
   - **系统原因**：为什么会走到那个点——降级路径、缺失的校验、错误配置没被发现、重试策略把小问题放大。
   - **假设层**：当时作决定的人（人或模型）相信了什么、没验证什么。这层最容易被跳过，也最值钱。
3. **找「第一次可以止损的信号」**：回看时间线，最早在哪一步就有证据表明方向错了？当时为什么没停下来？——复盘的价值在这里，不在追溯最后一个报错。
4. **审计防线**：列出本该拦住它的机制（测试、体检、超时、告警、验收标准、人工确认），逐个判断：没有？有但没触发？触发了但被忽略？**「有但没触发」比「没有」更危险**。
5. **产出护栏，不是检讨**：每条结论要么变成一个可执行的护栏（加一条校验、改一个默认值、写一条验收标准、加一个早停条件），要么明确标注「接受风险，因为 X」。**没有落到护栏的复盘等于没做**。

## 与其它模式的关系

- `debug` 定位并修复当前的故障；故障解决后再用本模式挖「为什么会发生」。
- `first-principles` 从事实层重建方案；本模式从失败现场提取事实层，两者可串用——复盘产出事实，first-principles 重建方案。
- 复盘的护栏要落地成代码/配置时用 `omd-plan` → `omd-execute`；只是写下结论时用 `omd-remember`。
- 事故涉及需求本身没定清（「做完了却不是用户要的」），先 `omd-deep-interview` 补验收标准。

## 收尾：HUD

用 `omd-hud` 输出四块：

- **时间线**：时刻 / 事件 / 来源 / 是否首次异常信号。
- **根因三层**：直接 / 系统 / 假设，逐层列证据。
- **防线审计表**：防线 / 应有作用 / 实际表现（无·未触发·被忽略·有效）/ 修补动作。
- **护栏清单**：动作 / 落点（文件·配置·验收标准）/ 负责人（人/自动化）/ 验证方式。

让「哪里错了、为什么没拦住、下次靠什么拦」一眼可见。

## 反模式

- **别写成检讨书**：「我们应该更仔细」不是结论。可执行动作才算。
- **别甩锅给单点**：「某个路径失效了」是直接原因不是根因；要问它为什么没被发现、为什么没有 fallback。
- **别只复盘最后一个报错**：第一次可止损信号往往在很早之前，找到它比追最后一行日志值钱十倍。
- **别无限上纲**：一次改错字不需要三层根因。复盘深度与损失成正比——10 分钟的返工用一句话记录就够。

# oh-my-dsh · Decision-record 决策记录

**存「为什么」而不是「是什么」**：代码记的是结论，`git log` 记的是改动，`remember` 记的是事实——但没有一个地方回答「当时为什么不选另一个方案、什么条件下该推翻」。本技能用轻量 ADR 补这一层。

与 `omd-remember` 的区别：remember 是散点笔记，decision-record 是结构化、带候选对比和失效条件的决策档案。

## 何时用

- 做了有权衡的架构/技术选型（选 A 不选 B，代价是什么）。
- 决定会影响后续多个任务，半年后可能有人问「为什么」。
- 用户说「记下这个决定」「留个依据」「以后别再讨论这个了」。
- 决策基于当时特定条件（性能数据、成本、团队规模）——条件会变，需要记录失效点。

**不要用**：纯事实记录（用 remember）、一次性的小选择、还没定的方案（先 deep-interview / ralplan）。

## 记录纪律

1. **写背景与约束**：一句话说清要解决什么问题、当时的硬约束是什么（时间、资源、兼容性、团队）。**没有约束的决策记录没有价值**——换个场景结论就变了。
2. **列候选，不只写赢家**：至少两个候选方案。只记录选中方案的 ADR 是自我背书，不是决策记录。
3. **依据要可追溯**：每条「因为 X 所以选 A」的 X 必须能指向证据——实测数据、官方文档、代码约束、当时的事故。**猜测标 `[假设]`，别混进事实**。
4. **写明代价**：选 A 放弃了什么？引入了什么新风险或维护成本？只写好处不写代价的决策记录是不可信的。
5. **写推翻条件**（本技能的核心）：什么证据出现时，这个决定就该重新评估？写成可观测的条件——「若 X 指标超过 Y」「若 Z 依赖被废弃」「若团队规模达到 N」——而不是「如果有更好的方案」。**没有推翻条件的 ADR 会变成教条**。
6. **落盘位置**：默认写到工作区 `docs/decisions/NNNN-简短标题.md`（NNNN 递增），或用户指定位置。文件frontmatter 带 `status: accepted|superseded` 和日期；被推翻时**不删除旧记录**，标 `superseded` 并指向新记录——保留决策演化链。

## 与其它模式的关系

- `first-principles` 重建出的方案、`ralplan` 共识规划的结果、`deep-analyze` 的权衡结论——都适合用本技能固化。
- 决策前需求没问清先 `deep-interview`；记完要落地用 `omd-plan`。
- `omd-remember` 记「发生了什么」，本技能记「为什么这么选」——两者互补，别混用。
- 复盘发现某个决策的前提错了，用 `omd-postmortem` 挖假设层，再用本技能标 `superseded`。

## 收尾：HUD

用 `omd-hud` 输出决策摘要：

- **决策卡**：背景 / 约束 / 选中方案 / 状态 / 日期。
- **候选对比表**：方案 / 优势 / 代价 / 依据来源。
- **推翻条件清单**：条件 / 如何观测 / 当前状态（未触发·已触发·需重估）。

让「选了什么、放弃了什么、什么时候该反悔」一眼可见。

## 反模式

- **别写成自我辩护**：只列赢家的好处、不给候选和代价——那是事后合理化，不是决策。
- **别编造依据**：当时没数据就写「基于当时经验判断 `[假设]`」，别伪造数字让记录看起来严谨。
- **别忘推翻条件**：这是 ADR 与普通笔记的唯一本质区别。写上「将来再说」等于没写。
- **别覆盖旧记录**：决定变了就标 superseded 并链接新旧，直接改写会让演化链断掉。
- **别为小选择建档案**：午饭吃什么不值得 ADR。决策成本要配得上记录成本。

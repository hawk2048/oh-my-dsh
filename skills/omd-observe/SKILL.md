# oh-my-dsh · Observe 运行时观测

**看现场，不看应该**：配置说一套、实际跑另一套，是排查里最贵的坑。本技能把「获取运行时证据」变成结构化纪律——先拿进程/日志/文件的真实状态，再谈推断。

与 `debug` 的区别：debug 从症状追根因并修；observe 只负责**把现场证据采集全**，不急着下结论和动手修。与 `visual-verdict` 的区别：后者只对截图/渲染做裁决，本技能管的是进程、端口、日志、配置文件、会话记录这类文本现场。

## 何时用

- 「配置改了但好像没生效」「到底跑的是哪个版本/哪个配置」。
- 服务行为与文档/预期不符，需要先用证据确认实际状态。
- 排查前收集现场：进程、端口、日志、资源占用、磁盘文件。
- 用户说「看下日志」「查下进程」「到底怎么回事」。

**不要用**：问题已经明确只要修（用 debug/execute）；纯代码静态分析（用 deepsearch）。

## 观测纪律

1. **问「应该是什么」之前先问「实际是什么」**：先采集运行态，不要带着假设去找证据。每次先记一句「我预期看到 X」——后面如果发现不是 X，这个落差本身是线索。
2. **进程的真实参数 > 任何配置/文档**：文档说默认走 A、配置说配了 B，但进程命令行才是实际在跑的 C。查进程启动参数（可执行文件、命令行参数、工作目录、环境变量），它是一切的基准真相。
3. **磁盘配置 ≠ 生效配置**：配置可能有多份副本（历史快照、用户级/系统级、缓存、内存态）。改了磁盘文件不代表运行中的进程读到了它——进程可能缓存了旧值，需要重启才加载。**永远确认「这份配置当前是否真的被读取」**，用修改时间、进程打开的文件、或应用自己的状态接口验证。
4. **注意元数据缓存延迟**：发布/部署/API 返回成功后，查询端可能有复制延迟显示旧状态。命令输出的成功标志是真相，元数据查询的旧值可能只是还没同步。**别因为查到旧值就重跑写操作**（重跑可能报冲突或造成重复），等复制窗口再查。
5. **日志要取对文件和时间段**：日志常按大小/时间轮转，当前文件可能是旧的，最新在轮转文件里。先按修改时间排序找到真正活跃的那个，再 grep。时间戳用系统命令取，别自己算。
6. **区分「信号」与「噪音」**：日志里大量 warning 是常态。只把与当前问题时间吻合、状态变化（首次出现/状态翻转/错误码）的记录列为信号；其余标注「背景噪音」。
7. **会话/历史记录是高价值现场**：很多系统的对话、操作、事件历史存在压缩的 JSONL/数据库里。先找记录文件（注意压缩格式），看事件类型分布定位异常（重试、失败、超时、状态翻转），再提取关键事件的时间线。
8. **每次观测留证据**:结论必须带来源——文件路径、命令行、时间戳、字段值。**「看起来像」「应该是」不算证据**。

## 与其它模式的关系

- 先 observe 收集证据，再 `debug` 定位根因并修；observe 的输出是 debug 的输入。
- 发现配置与预期不符且原因在历史决策，转 `omd-postmortem`；需要把「如何验证这类问题」固化，用 `omd-skillify`。
- 观测结论要长期留存时用 `omd-remember`；要作为决策依据用 `omd-decision-record`。
- 只想知道代码在哪、怎么实现，用 `omd-deepsearch`。

## 收尾：HUD

用 `omd-hud` 输出：

- **现场快照表**：检查项 / 预期 / 实际 / 来源（命令·文件·时间）/ 判定（符合·不符·待查）。
- **证据链**：关键事件时间线，每条带来源。
- **落差清单**：所有「实际 ≠ 预期」的点，按可疑度排序——这是下一步 debug 的入口。

让「看到了什么、哪条对不上、下一步查哪里」一眼可见。

## 反模式

- **别改完就宣布生效**：磁盘配置改了不等于运行态变了。没确认进程加载就是没验证完。
- **别被旧元数据骗去重跑**：查到旧状态先等复制窗口，别急着重发写操作。
- **别只 grep 一个日志**：先找活跃文件，否则查的是历史归档。
- **别把观测当诊断**：observe 只列事实和落差，不急于下「根因是 X」的结论——那是 debug 的事。
- **别裸奔下结论**：任何判断都要能指回一条具体证据，没有就老实标「待查」。
